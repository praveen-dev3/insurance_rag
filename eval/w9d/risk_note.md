**Who wrote it:** the claims platform team, not us - code and prompts we have never reviewed, running as a subprocess we spawn but do not audit, inside `tools/w9d_agent.py`'s trust boundary the moment it's added to `tools/data/w9d_mcp_config.json`.
**What it can reach:** by design, every open claim's status and full adjuster-note history, by claim number alone - no per-claim consent check, and (per `get_adjuster_notes`'s own description) notes are returned unsanitized, the exact injection channel `tools/w8d_injection.py` already exploited on Week 7's equivalent data.
**What it logs:** unknown to us - our `wire.json` capture only sees our side of the stdio pipe; a networked version of this same server (SSE/HTTP, once it leaves this stdio simulation) could retain every claim number and note we send it on infrastructure we don't control and can't inspect.
**What a stolen token could do:** in this stdio build there is no token, only implicit process trust - but the moment this becomes a networked deployment with a shared credential, a leaked one reads every adjuster note on every open claim, with no scoping to stop it (see the bonus gateway's scoped-token idea, not implemented here).
**Verdict:** don't ship as configured - ship only behind a gateway that scopes the token to `get_claim_status` alone (denying `get_adjuster_notes` by default) and audit-logs every call by caller, tool and claim number, per the bonus challenge.
