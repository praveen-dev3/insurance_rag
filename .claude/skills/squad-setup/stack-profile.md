# Stack profile — template + how to generate it

`squad-setup` generates ONE file, **`.claude/stack-profile.md`** at the repo root, that captures this project's tech stack: exact commands, test conventions, and a framework-specific review lens. Every squad agent (planner, implementer, verifier, code-reviewer) reads it at the start of a lane, so the whole pipeline behaves according to the project's stack instead of guessing.

One generated file, read by all agents — no per-project rewriting of the agent files, no drift.

---

## How to generate it (setup step)

1. **Detect the stack.** Inspect the repo:
   - Language(s): file extensions, `package.json` / `pyproject.toml` / `go.mod` / `Cargo.toml` / `pom.xml` / `build.gradle` / `Gemfile` / `composer.json` / `*.csproj`.
   - Frameworks: dependency lists (e.g. `fastapi`, `django`, `react`, `nestjs`, `spring-boot`, `rails`, `gin`, `axum`).
   - Package manager: the lockfile (`uv.lock`, `poetry.lock`, `pnpm-lock.yaml`, `yarn.lock`, `package-lock.json`, `go.sum`, `Cargo.lock`, `Gemfile.lock`).
   - Monorepo: multiple packages under `apps/` / `packages/` / `services/`, workspace config.
2. **Resolve the real commands.** Prefer scripts the repo already defines (`package.json` scripts, `Makefile` targets, `pyproject.toml [tool.*]`, `tox.ini`, `justfile`) over inventing them. If the repo pins a linter/formatter/type-checker in config, use it (don't assume `ruff` if it's `flake8`).
3. **Pick the review lens** from the per-stack cheatsheet below, matching the detected language + framework.
4. **Write `.claude/stack-profile.md`** using the template. Leave a `TODO:` marker for anything you couldn't determine rather than guessing.
5. **Multi-stack repos** (e.g. a TS frontend + Python backend): list each stack as its own block under Commands and Review lens, tagged with the directory it applies to. Agents pick the block matching the files their lane touches.

Regenerate after a major stack change (new framework, package-manager switch). Note in `CLAUDE.md` that this file is generated.

---

## Template (`.claude/stack-profile.md`)

```markdown
# Stack Profile
<!-- Generated by squad-setup. Read by every squad agent for stack-specific
     commands, test conventions, and review lens. Regenerate after a major
     stack change. TODO markers = unresolved; fill before relying on them. -->

**Languages:** <e.g. Python 3.12>
**Frameworks:** <e.g. FastAPI, SQLAlchemy, Pydantic v2>
**Package manager:** <e.g. uv>
**Monorepo:** <no | yes — layout>

## Commands
| Purpose | Command | Run from |
|---|---|---|
| Lint | <cmd> | <dir> |
| Format check | <cmd> | <dir> |
| Typecheck | <cmd> | <dir> |
| Unit tests | <cmd> | <dir> |
| Targeted test | <cmd pattern> | <dir> |
| Integration / e2e | <cmd> | <dir> |
| Build | <cmd> | <dir> |

## Test conventions
- Framework: <e.g. pytest>. New code → <where sibling tests go and in what style>.
- <fixtures / mocking / factory conventions the repo uses>

## Review lens (stack-specific — weight in addition to the generic security lens)
- <framework-specific traps from the cheatsheet, pruned to what applies>

## High-stakes areas (this project)
- <auth, payments, migrations, public API, data integrity — fill per project>
```

## Per-stack cheatsheet

Use these to fill the **Commands** defaults and the **Review lens**. Verify each command against the repo's actual config before writing it — these are starting points, not truth.

### Python
- Commands: lint `ruff check .` (or `flake8`); format `ruff format --check .` (or `black --check .`); typecheck `mypy <pkg>` (or `pyright`); test `pytest` / targeted `pytest path::test`; e2e `pytest -m integration`; build `uv build` / `python -m build`.
- Test framework: pytest (sibling `test_*.py`, fixtures) or unittest — match what exists.
- Review lens: mutable default args (`def f(x=[])`); bare `except:` swallowing errors; `is` vs `==` on values; un-awaited coroutines / blocking I/O in async handlers; SQLAlchemy N+1 (missing `selectinload`); Pydantic validation bypass (`.construct()`); f-string/`%`-built SQL; `assert` used for runtime validation (stripped under `-O`).

### JavaScript / TypeScript
- Commands: lint `eslint .` / `npm run lint`; format `prettier --check .`; typecheck `tsc --noEmit`; test `jest` / `vitest` / `npm test`; e2e `playwright test` / `cypress run`; build `npm run build`. Use the repo's package manager (pnpm/yarn/npm) from the lockfile.
- Review lens: floating/un-awaited promises & unhandled rejections; `null`/`undefined` deref; `==` vs `===`; missing input validation on handlers (DTO/zod/Joi); N+1 DB queries in loops; `any` escapes; unbounded `Promise.all` fan-out; secrets in bundles.

### Go
- Commands: lint `golangci-lint run`; vet `go vet ./...`; test `go test ./...` / targeted `go test -run TestX ./pkg`; race `go test -race ./...`; build `go build ./...`.
- Review lens: unchecked errors; goroutine leaks / missing `context` cancellation; data races on shared state; `nil` map writes; loop-variable capture (pre-1.22); `defer` in loops; unclosed resources (`rows`, `resp.Body`).

### Rust
- Commands: lint `cargo clippy -- -D warnings`; format `cargo fmt --check`; test `cargo test`; build `cargo build`.
- Review lens: `.unwrap()`/`.expect()` on fallible paths; `panic!` in libraries; blocking calls in async; `unsafe` blocks without justification; integer overflow in release; holding a lock across `.await`.

### Java / Kotlin
- Commands: lint/format `./gradlew spotlessCheck` (or checkstyle); test `./gradlew test` / `mvn test`; build `./gradlew build` / `mvn package`.
- Review lens: `NullPointerException` paths / missing `Optional`; resource leaks (use try-with-resources); unvalidated request DTOs; N+1 (JPA lazy loading); mutable shared state / thread-safety; swallowed exceptions.

### Ruby
- Commands: lint `rubocop`; test `rspec` / `rails test`; build/setup `bundle install`.
- Review lens: mass-assignment / strong-params bypass; N+1 (missing `includes`); SQL built by interpolation; `rescue => e` swallowing; unsafe `send`; missing scope on ActiveRecord queries.

### PHP
- Commands: lint `phpcs` / `php-cs-fixer`; static analysis `phpstan analyse` / `psalm`; test `phpunit`; build via composer.
- Review lens: SQL injection via string concat (use prepared statements); unvalidated superglobals; mass assignment; `==` vs `===` loose comparison; N+1 (eager-load); secrets in code.

For a stack not listed, follow the same shape: real lint/format/typecheck/test/build commands from the repo's config, plus the 5-8 most common correctness/security traps for that language + framework.
