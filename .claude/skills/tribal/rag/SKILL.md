# rag

## Business Purpose

`rag/` answers natural-language questions about insurance policy PDFs (base policy wordings plus endorsement forms) with every factual claim tied to a citation that resolves to exactly one stored row in the index. The domain constraint that shapes the whole library is that an insurance fact is meaningless without its provenance: exclusion code `E-17` on Form `HO-0304` ed. `03-24` (homeowners) and `E-71` on `DP-0208` (dwelling fire) say nearly the same words and have different dispositions (`rag/metadata.py:1-21`). So the package is not "vector search plus an LLM" — it is a pipeline built so that (a) a chunk can never lose the form/edition/policy-line that scopes it, (b) a citation is checkable by primary-key lookup rather than by rereading prose (`rag/generation.py:65-68`, `rag/generation.py:164`), and (c) when the answer is wrong you can prove whether retrieval or generation caused it (`rag/diagnostics.py:1-17`).

## Why It Exists

- **One library, three front ends.** `main.py` (CLI), `server.py` (FastAPI/SSE) and `evaluate.py` all drive `RagEngine` (`rag/engine.py:49`) so a measured improvement in the evaluator is the same code path the user hits. `rag/config.py` exists specifically so the three cannot drift apart (`rag/config.py:1-7`).
- **No LangChain/LlamaIndex, deliberately.** README "Why no LangChain or LlamaIndex". Every stage is hand-written so the trace can be exhaustive; `RetrievalTrace` (`rag/retrieval.py:281`) is the product, not a debug aid.
- **Everything except final generation runs locally.** Embeddings (`sentence-transformers`) and the cross-encoder reranker are local; only the Groq call leaves the machine (`rag/llm.py:15`). That is why model loads are lazy and lock-guarded and why `require_api_key` (`rag/config.py:208`) is deferred — indexing and retrieval-only evaluation must work with no credentials.
- **The four chunking strategies are an experiment that was resolved, not dead code.** `fixed`/`recursive`/`sentence` all pack token windows; `structure` splits on the documents' own landmarks and stamps a provenance banner on every chunk (`rag/chunking.py:435-465`). `recursive` was the earlier default and is structure-aware about *prose but blind to tables* — an exclusion table has no blank lines, so `recursive` falls through to splitting on `". "` and cuts the table wherever 220 tokens ends, orphaning `E-17` from `HO-0304` (`rag/chunking.py:25-30`). `structure` is now the default (`rag/config.py:66`). The others are kept so `sweep_chunking` can still reproduce the comparison.
- **Incremental sync was added after a full-rebuild-only design.** The old defence was that content-hash chunk ids make an edit rename every downstream chunk, so diffing costs more than rebuilding. That is true *within* a document and false *across* documents, so reconciliation happens at file granularity (`rag/indexing.py:18-24`). Both lifecycles are still present and are not interchangeable (`rag/indexing.py:7-16`).
- **Query rewriting and HyDE are implemented and off by default because they were measured.** Rewriting dropped hit@1 from 0.969 to 0.781 — it paraphrases `TN06BJ2206` and "Section II-1(ii)" into generic wording and BM25 loses the exact token it keys on (README "Measured results"). HyDE changed nothing on this corpus. Do not turn either on as an "obvious improvement".
- **The `-8.0` reranker floor is a deliberate, costed trade.** Lowering it to `-12` fixes the one remaining retrieval failure (q27, a bare key/value table pypdf mangled) *and* lets junk survive for all 6 out-of-scope questions instead of 3. The floor is what produces "I don't know", so the default stays (README "What the change did *not* fix").
- **Ground truth is page-level on purpose** (`rag/evaluation.py:8-10`, `rag/diagnostics.py:370-373`) so labels survive a chunking sweep, with a stricter chunk-id classifier added later for experiments that pin the chunker (`rag/diagnostics.py:134-142`).
- **Note:** `rag/claims.py` and `rag/tracing.py` also live in this package but are newer and are not imported by `rag/engine.py` or `rag/__init__.py`; they are driven from `tools/`. This skill covers the engine path only.

## Gotchas

### The index signature: what forces a rebuild and what silently reuses a stale index

`index_signature()` (`rag/config.py:197-205`) folds in exactly seven things: schema version (`rag/config.py:186`), `CHUNK_STRATEGY`, `CHUNK_SIZE`, `CHUNK_OVERLAP`, `SENTENCE_OVERLAP`, `EMBEDDING_MODEL`, `HNSW_SPACE`. Change any of those and `sync_collection` drops and rebuilds the whole collection (`rag/indexing.py:592-601`), because chunks written under the old metadata schema cannot be deleted by a `source_file`-keyed delete and would survive as unattributable duplicates that still answer queries (`rag/indexing.py:583-587`).

- **The three HNSW recall knobs are NOT in the signature.** `HNSW_EF_CONSTRUCTION`, `HNSW_EF_SEARCH`, `HNSW_MAX_NEIGHBORS` (`rag/config.py:95-97`) reach Chroma only through `collection_configuration()` at `create_collection` time (`rag/indexing.py:445`, `rag/indexing.py:612`). Setting `HNSW_EF_SEARCH=400` against an existing `chroma_db/` changes **nothing** — no rebuild is triggered and the stored graph keeps its original parameters. You must `--reindex` (or delete `chroma_db/`) for those to take effect, and there is no warning that you didn't.
- **`CHUNK_OVERLAP` and `SENTENCE_OVERLAP` are in the signature but the default strategy ignores them.** `_structure_chunks` (`rag/chunking.py:468`) never applies overlap. So bumping `CHUNK_OVERLAP` under `CHUNK_STRATEGY=structure` costs you a full re-embed of the corpus and produces a byte-identical index.
- **`RERANKER`, `TOP_K`, `RRF_K`, `DENSE_TOP_K`, `USE_MMR`, `USE_HYDE`, `RERANK_CANDIDATES` are correctly absent** from the signature — they are query-time only. Changing them needs no reindex.
- **Everything in `config.py` is read at import time.** `load_dotenv()` runs at module import (`rag/config.py:13`) and every knob is a module-level constant. Mutating `os.environ` after `import rag` has no effect; several are also frozen as default argument values (`rag/retrieval.py:628`, `rag/retrieval.py:693`, `rag/retrieval.py:738`, `rag/engine.py:150-152`), so monkeypatching the module attribute in a test still won't move them.

### Embedding prefixes — the silent-wrong-results trap

- Retrieval models here are **asymmetric**: `bge-*` puts an instruction on the query and nothing on the passage (`rag/embeddings.py:36`), `e5-*` needs `query: ` / `passage: ` on both sides (`rag/embeddings.py:52-53`), `minilm` needs neither. Dropping the prefix does not error — the vectors still come out, just worse (`rag/embeddings.py:9-11`). Never call `_encode` or `SentenceTransformer.encode` directly; go through `embed_query` / `embed_passages` (`rag/embeddings.py:131-138`).
- Collections are always opened and created with `embedding_function=None` (`rag/indexing.py:356-359`, `rag/indexing.py:446`) precisely so nobody can accidentally use `collection.query(query_texts=...)`, which would embed with Chroma's default model and no prefix. Adding a `query_texts` call is a silent correctness regression, not a crash.
- `normalize_embeddings=True` (`rag/embeddings.py:124`) is load-bearing twice over: Chroma is configured for cosine space, and `mmr_order` treats the dot product *as* the cosine (`rag/retrieval.py:443`). Any code path that produces un-normalised vectors silently corrupts MMR's diversity term.
- The `max_tokens` field in each model spec (`rag/embeddings.py:31`, `:39`) is **documentation only** — it is surfaced by `describe()` and never enforced. `CHUNK_SIZE=220` is justified as staying under a 256 word-piece limit (`rag/config.py:68-70`), but chunk sizes are counted in tiktoken `cl100k_base` tokens (`rag/chunking.py:79`), a different tokenizer from the encoders'. Raising `CHUNK_SIZE` much past the default risks silent tail truncation inside the encoder with no log line.

### Retrieval stage ordering and pool sizes

- **`top_k` does not widen recall.** `search()` calls `dense_search`/`sparse_search` with no `top_k` (`rag/retrieval.py:928`, `rag/retrieval.py:940`), so both use their import-time defaults of 20; and `fuse` is called with no `limit` (`rag/retrieval.py:949`), so it always truncates to `RERANK_CANDIDATES=20`. Passing `top_k=10` (CLI `--top-k`) only changes how many survive reranking. To widen the candidate pool you must change `DENSE_TOP_K`/`SPARSE_TOP_K`/`RERANK_CANDIDATES` in the environment.
- **MMR runs *before* reranking and truncates the pool.** With `use_mmr` on, `diversify` returns at most `max(mmr_pool, top_k)` = 10 candidates by default (`rag/retrieval.py:968`), so the cross-encoder never sees the other 10 fused candidates. MMR can drop the correct chunk before the only stage that reads query and passage jointly ever scores it. `USE_MMR` defaults to False (`rag/config.py:128`).
- **MMR is scored against `dense_query`, not the question** (`rag/retrieval.py:966`). Under HyDE, `dense_query` is the *fabricated* passage (`rag/query.py:192`), so diversity is measured relative to invented text.
- **`trace.dense` and `trace.sparse` are derived from the fused list, not from the raw hit lists** (`rag/retrieval.py:951-956`). A chunk that was in the dense top-20 but fell outside the fused top-20 does not appear in `trace.dense` at all. Consequently `classify_by_chunk_id`'s "it was never retrieved by any retriever" verdict (`rag/diagnostics.py:191-192`) actually means "not in the top `RERANK_CANDIDATES` after fusion" — do not read it as proof the retrievers missed it.
- **`trace.reranked` ignores the relevance floor** (`rag/retrieval.py:992-1000`): it is every candidate sorted by rerank score. Only `trace.final` is post-floor and post-`top_k`. `evaluate_retrieval` scores both stages (`rag/evaluation.py:259-261`), so a `reranked` metric that beats `final` means the floor dropped the answer, not that reranking regressed.
- **The floor is applied after truncation to `top_k`** (`rag/retrieval.py:868-874`), so `dropped_below_floor` only ever contains chunks that were already in the top-k — it is not a list of everything rejected.
- **Filter parity between the dense and sparse halves is a hand-maintained invariant.** `build_where` (`rag/retrieval.py:348`) builds the Chroma clause; `matches_filters` (`rag/retrieval.py:393`) re-implements the identical predicate in Python for BM25. If you add a filter key to one and not the other, nothing fails loudly — the filtered-out documents leak back in through fusion and it looks like a retrieval-quality problem (`rag/retrieval.py:397-401`). Page bounds are **overlap** semantics on both sides (`rag/retrieval.py:379-382`, `rag/retrieval.py:416-422`).
- Filter values are exact string matches against a controlled vocabulary — no substring matching, so "motor" will not match "motorhome" (`rag/retrieval.py:336-339`). Note `sources` filters on the `source` metadata field, while document removal keys on `source_file` (`rag/indexing.py:635`); they are equal in practice but are separate columns.
- **`UNSPECIFIED = "unspecified"` is a sentinel, not cosmetics** (`rag/metadata.py:29`): Chroma rejects `None` in a metadata value, and an *absent* key silently fails an equality filter rather than erroring. Never write `None` into chunk metadata.
- BM25 drops zero-scoring chunks and breaks out of the ranked scan at `score <= 0` (`rag/retrieval.py:722`), so `sparse_search` legitimately returns fewer than `SPARSE_TOP_K`. RRF constant is 60 from the original paper, ranks are 1-based, and a chunk's score is summed over the lists it appears in (`rag/retrieval.py:779`, `rag/retrieval.py:786`).
- **`dense_search` mutates the retriever.** A hit that Chroma returns but the retriever has never seen is adopted into `self.records` on the fly (`rag/retrieval.py:659-679`) — but *not* into `self._order`, so it never enters the BM25 corpus and never becomes findable by keyword until `refresh()` is called. It also has `vector=None`, so MMR silently re-encodes it (`rag/retrieval.py:614-622`). It does appear in `sources()` / `page_range()`, which drive the filter UI.
- `BM25Okapi` is only constructed when the corpus is non-empty, because it divides by mean document length (`rag/retrieval.py:563`); an empty index makes `sparse_search` return `[]` rather than raising.

### Chunking — where a chunk boundary can lose the answer

- **`_pieces_for` ignores the caller's `chunk_size` for the `recursive` strategy.** It splits with the module-level `CHUNK_SIZE` (`rag/chunking.py:269`) and is called with no size argument (`rag/chunking.py:676`), while `_pack` then uses the passed-in `chunk_size` (`rag/chunking.py:685`). So `create_chunks(strategy="recursive", chunk_size=400)` — which is exactly what `sweep_chunking` does (`rag/evaluation.py:479-485`) — pre-splits at 220 and packs at 400. The sweep numbers for non-default recursive sizes are measuring a hybrid, not the size you asked for.
- **Only `structure` guarantees provenance is inside the chunk text.** The other three label chunks by scanning the packed result after the fact (`rag/chunking.py:688`, `rag/chunking.py:593-601`); a chunk that begins mid-table has no clause marker in it and gets `UNSPECIFIED`. All four strategies still stamp `source_file`/`form_number`/`policy_line`/`edition_date` on the *metadata* (`rag/chunking.py:637-641`), so metadata filters work identically across a comparison — the difference is only in what the LLM can read.
- `_structure_chunks` applies the token budget **last**, after "never span two clauses" and "an exclusion row is atomic" (`rag/chunking.py:472-482`), and reserves banner tokens with a hard 60-token minimum floor (`rag/chunking.py:530`). If the provenance banner ever grows past `chunk_size - 60`, that floor silently overrides the budget.
- A paragraph too large to fit is re-split on prose boundaries rather than dropped, and each fragment is flushed as its own chunk carrying the same page range (`rag/chunking.py:550-569`) — page ranges on those fragments are the whole original unit's, not the fragment's.
- **Ordering constraint in ingest:** `extract_document_metadata` is called on the *raw* first page (`rag/indexing.py:188`) and `strip_page_furniture` runs afterwards, per page (`rag/indexing.py:198`). The running-header fallback for form/edition/policy-line matches the exact line the stripper deletes (`rag/metadata.py:51-53` vs `rag/metadata.py:110-114`). Reorder those two and every document whose front matter is absent silently degrades to `UNSPECIFIED`.
- Metadata extraction is three fallbacks in descending trust — front matter, running header, filename — and anything matching none of them degrades to `UNSPECIFIED` rather than raising (`rag/metadata.py:122-131`). `KNOWN_DOCUMENTS` (`rag/metadata.py:34`) is applied first and, because later steps only fill fields still equal to `UNSPECIFIED` (`rag/metadata.py:154`), a hardcoded entry wins over the document's own front matter.
- Chunk ids are `{source}#{sha1(text)[:16]}` with an occurrence suffix for genuine duplicates (`rag/indexing.py:225-256`). This is what makes a printed citation still resolve after an unrelated document is re-ingested — and it is why `add_chunks` must `upsert`, not `add` (`rag/indexing.py:407-409`).

### Fail-open behaviour and silent fallbacks

- **A failed LLM call is returned as the answer string, not raised** (`rag/generation.py:280`). A decommissioned `LLM_MODEL` therefore reads as a total quality collapse — every answer becomes `"The language model request failed: ..."` and every citation check reports zero citations — which looks exactly like a prompting regression. This has happened before (`rag/config.py:36-43`). `is_generation_error` (`rag/generation.py:198`) exists to tell the two apart, but **nothing in `rag/` calls it** — not `rag/evaluation.py`, not `rag/diagnostics.py`. Only `tools/` does. So `evaluate_answers` (`rag/evaluation.py:362`) will label an outage as `generation_failure`. Check for the marker first, always.
- **The LLM judge fails open to `OK`.** If the judge call raises or returns unparseable JSON, `classify_with_judge` returns `label=OK` (`rag/diagnostics.py:537-543`). A dead `UTILITY_MODEL` or a missing `GROQ_API_KEY` therefore produces a clean bill of health for every question.
- **The three query transforms are best-effort and swallow `OpenAIError`, returning the original question** (`rag/query.py:80-81`, `rag/query.py:117-118`, `rag/query.py:157-158`). A silently-degraded query is the intended trade, but it means "rewriting is enabled" and "rewriting happened" are different facts — check `queries["rewritten"]` on the trace. A rewrite that collapses to under two words is also discarded (`rag/query.py:122`).
- **Bare `except Exception` swallows a lot in the index lifecycle:** `indexed_fingerprints` returns `{}` on any read failure (`rag/indexing.py:511-514`), which makes every document look un-indexed and triggers a full re-ingest; `delete_collection` failures are ignored in both rebuild paths (`rag/indexing.py:436-439`, `rag/indexing.py:605-608`); Chroma's max batch size falls back to 1000 (`rag/indexing.py:398-401`); `open_collection` failure means "no collection, create one" (`rag/indexing.py:578-581`).
- **Unreadable PDFs and unparseable pages are logged and skipped, not fatal** (`rag/indexing.py:156-160`, `rag/indexing.py:166-173`). A scanned page is simply absent from the index; the later "why can't it find this?" looks like a retrieval bug. Only a corpus where *nothing* extracted raises (`rag/indexing.py:210-214`), and a whole-document extraction failure only warns (`rag/indexing.py:180-186`).
- `verify_ingest` (`rag/indexing.py:298`) reads as the source_file guarantee but its predicate requires a chunk to have *both* no metadata `source_file` **and** no `source` (`rag/indexing.py:307-312`), and `create_chunks` always sets `source` (`rag/chunking.py:694`). The real guarantee is the unconditional fallback in `chunk_metadata` (`rag/indexing.py:276`) and its read-path mirror in `provenance_of` (`rag/retrieval.py:107`). Don't weaken either.
- `server.py` deliberately does **not** abort startup when the engine fails to build; the error is stashed and turned into a 503 by `get_engine` (`server.py:119-124`, `server.py:139-155`) so `/api/health` stays reachable.

### The two classifiers must not be conflated

There are two independent axes of confusion here, and both bite.

1. **Retrieval failure vs generation failure.** This is the module's whole reason to exist (`rag/diagnostics.py:1-17`). `context_sufficient` and `answer_grounded` are kept as separate fields rather than merged into the label (`rag/diagnostics.py:80-86`) precisely so a surprising label can be checked. Never collapse them.
2. **Two *different classifier functions*, with different ground truth granularity.**
   - `classify_with_ground_truth` (`rag/diagnostics.py:365`) judges at **page** level (`rag/diagnostics.py:393-396`) so labels survive a chunking sweep. This is what `evaluate_answers` uses.
   - `classify_by_chunk_id` (`rag/diagnostics.py:132`) judges at **chunk-id** level (`rag/diagnostics.py:170`) — stricter, and only valid for experiments that pin the chunker, because chunk ids move whenever chunking changes (`rag/diagnostics.py:134-142`).
   Swapping one for the other silently changes what the numbers mean. They also do not agree on how "R" and "G" split, so mixing them across runs makes the R/G ratio — the thing the whole failure analysis turns on — meaningless.

Related traps in the same area:

- **Two different refusal detectors.** `generation.py:is_refusal` (`rag/generation.py:210`) is an exact match on the whole stripped string — an answer that emits the refusal sentence *then* answers anyway is not a refusal. `diagnostics.py:answer_refuses` (`rag/diagnostics.py:341`) is a loose substring match, because the model paraphrases even at temperature 0. They give different verdicts on the same string by design; pick the one that matches your intent.
- **`answer_refuses("")` and `answer_refuses(None)` both return `True`** (`rag/diagnostics.py:349-350`). `classify_by_chunk_id` special-cases `answer is None` (`rag/diagnostics.py:225-236`) with an explicit comment that returning `GENERATION_FAILURE` there would mislabel every retrieval success — but an empty *string* is not caught by that guard and will be labelled a generation failure.
- **`MISSED_REFUSAL` is the hallucination case and is *not* separately reported in the three-way tally.** `TASK_LABELS` maps both `CORRECT_REFUSAL` and `MISSED_REFUSAL` to `"Not-In-Corpus"` (`rag/diagnostics.py:67-73`) — lossy in exactly the direction that hides an unsafe system. Report `Diagnosis.label`, not just `task_label`.
- `normalize_for_match` (`rag/diagnostics.py:295`) folds Unicode dashes/spaces to ASCII before substring checks. Without it, a model that writes `E‑17` with a non-breaking hyphen fails an `answer_contains` check for `E-17` and inflates G at the expense of R (`rag/diagnostics.py:271-277`). Any new answer-content check must go through it.
- `answer_contains` anchors are identifiers and figures only, so `generation_failure` is undercounted by construction (README "Known limits").

### Reranker floors do not transfer between models

`min_score` resolves as: explicit `min_score` argument, else `MIN_RERANK_SCORE` env override, else the reranker's own default (`rag/retrieval.py:866`, `rag/rerankers.py:48-55`). The defaults live on different scales — `ms-marco` `-8.0` (`rag/rerankers.py:192`), `bge` `-5.0` (`rag/rerankers.py:199-201`), Cohere `0.05` because it emits 0-1 relevance (`rag/rerankers.py:132`). Setting `MIN_RERANK_SCORE=-8` and then switching `RERANKER=cohere` gives you a floor of `-8` on a 0-1 scale, i.e. **no floor at all** — refusals stop working and out-of-scope questions start getting answered. Likewise `RERANKER=none` (`NullReranker` scores `-index`, `rag/rerankers.py:81`) has no default floor and preserves fusion order; it is the control arm, not a performance option.

### Miscellaneous

- **The engine answers the *transformed* question, not the user's words.** `generate_answer` is handed `queries["search_query"]` (`rag/engine.py:237`), and `retrieve` is handed `queries["condensed"]` as the trace question (`rag/engine.py:198`). With `USE_QUERY_REWRITE=1` the LLM is answering a machine paraphrase of what the user typed. `trace.question` is patched back to the original afterwards (`rag/engine.py:210`).
- **`RagEngine._lock` covers only `retrieve` and `reindex`** (`rag/engine.py:161`, `rag/engine.py:134`). Query transforms, generation and `stats()` run unlocked. `stats()` reads `self.retriever` without the lock, so it can observe the pre-reindex retriever mid-rebuild.
- The HyDE draft is invented text and must never enter the grounded prompt or the UI (`rag/query.py:136-139`) — it exists only as a retrieval probe. It *is* included in `queries` on the trace, so anything that renders the trace must not present it as a source.
- `sweep_retrieval` **mutates the caller's variant dicts** — `variant.pop("label", ...)` (`rag/evaluation.py:442`). Re-running a sweep over the same list gives different labels the second time.
- `load_golden_set` treats a missing file as a hard error, because silently evaluating zero questions reports a perfect score (`rag/evaluation.py:71-81`).
- `percentile` uses nearest-rank, not interpolation, and on a small set p95 is effectively the maximum — a single observation, not a tail (`rag/evaluation.py:177-214`).
- `plan_sync` treats a document whose chunks *disagree* about their own fingerprint as stale, because that means two runs wrote it (`rag/indexing.py:549-552`), and stale documents have their old chunks deleted before re-ingest so a shrinking edit cannot leave orphans that still answer queries (`rag/indexing.py:652-656`).
- `stream_answer` skips stream events with no `choices` — the final Groq chunk carries usage data only and would otherwise raise `IndexError` (`rag/generation.py:309-312`).

## Flow

Canonical happy path, `server.py POST /api/chat` (or `main.py` → `RagEngine.ask`):

1. **Boot.** `RagEngine.__init__` opens a `chromadb.PersistentClient` at `CHROMA_PATH` (`rag/engine.py:63`) and calls `load_or_build_collection` (`rag/indexing.py:679`).
2. **Reconcile the index.** `sync_collection` (`rag/indexing.py:564`) lists PDFs (`rag/indexing.py:71`), opens the collection, and compares the stored `index_signature` against the current one — mismatch means drop and rebuild (`rag/indexing.py:592-601`). Otherwise `plan_sync` (`rag/indexing.py:528`) diffs per-file SHA-256 fingerprints (`rag/indexing.py:93`) against the fingerprints stamped on the stored chunks (`rag/indexing.py:501`) to produce `to_ingest` / `to_remove` / `unchanged`. Nothing to do → return the collection untouched (`rag/indexing.py:623-629`).
3. **Ingest the deltas.** Withdrawn and stale documents are deleted by `source_file` (`rag/indexing.py:635`, `rag/indexing.py:656`). `load_documents` (`rag/indexing.py:139`) reads pages with pypdf, parses document metadata off the raw first page (`rag/indexing.py:188`), then strips page furniture per page (`rag/indexing.py:198`).
4. **Chunk.** `create_chunks` (`rag/chunking.py:628`) groups pages by source and, for the default `structure` strategy, runs `_parse_units` (`rag/chunking.py:322`) → `_structure_chunks` (`rag/chunking.py:468`), prefixing every chunk with the `_provenance` banner (`rag/chunking.py:435`).
5. **Embed and write.** `add_chunks` (`rag/indexing.py:362`) derives content-hash ids (`rag/indexing.py:225`), builds flat Chroma metadata (`rag/indexing.py:259`), encodes all texts in one batched `embed_passages` call (`rag/indexing.py:394`), and `upsert`s in max-batch-size slices (`rag/indexing.py:409`).
6. **Build the sparse side.** `HybridRetriever.__init__` (`rag/retrieval.py:493`) reads every row back — documents, metadatas and stored embeddings — into `_Record`s and builds an in-memory `BM25Okapi` over the tokenised corpus (`rag/retrieval.py:510-565`). The vector store stays the single source of truth for what is indexed.
7. **Transform the question.** `RagEngine.prepare` (`rag/engine.py:190`) calls `query.transform` (`rag/query.py:167`): condense against history (`rag/query.py:176`), optional rewrite (`rag/query.py:178`), optional HyDE (`rag/query.py:182`), yielding `search_query` (BM25 + reranker, `rag/query.py:180`) and `dense_query` (embedded, `rag/query.py:192`).
8. **Enter retrieval under the lock.** `RagEngine.retrieve` (`rag/engine.py:161`) → `HybridRetriever.search` (`rag/retrieval.py:885`), which validates the mode, resolves `use_mmr`/reranker, and seeds the `RetrievalTrace` with the full effective config (`rag/retrieval.py:905-923`).
9. **Stage 1a — dense.** `dense_search` (`rag/retrieval.py:628`) embeds `dense_query` with the model's query prefix (`rag/retrieval.py:640`) and queries Chroma with a `where` clause from `build_where` (`rag/retrieval.py:642-646`), returning `(id, distance)` pairs.
10. **Stage 1b — sparse.** `sparse_search` (`rag/retrieval.py:693`) tokenises `search_query` (`rag/retrieval.py:63`), scores the BM25 corpus, drops zero-scorers, and applies `matches_filters` per hit (`rag/retrieval.py:710-730`).
11. **Stage 2 — RRF fusion.** `fuse` (`rag/retrieval.py:738`) accumulates `1/(60 + rank)` per list (`rag/retrieval.py:779`, `rag/retrieval.py:786`), sorts, stamps `fused_rank`, and truncates to `RERANK_CANDIDATES` (`rag/retrieval.py:788-797`). `trace.dense` / `trace.sparse` / `trace.fused` are recorded from this list (`rag/retrieval.py:951-957`).
12. **Stage 3 — MMR (off by default).** `diversify` (`rag/retrieval.py:803`) re-embeds the query, reads candidate vectors back from the index, and runs `mmr_order` (`rag/retrieval.py:431`), truncating to `max(mmr_pool, top_k)` (`rag/retrieval.py:961-976`).
13. **Stage 4 — rerank + floor.** `rerank` (`rag/retrieval.py:840`) scores `(search_query, chunk.text)` pairs with the cross-encoder, sorts descending, keeps `top_k`, then splits on the relevance floor into `kept` / `dropped` and stamps `final_rank` (`rag/retrieval.py:855-879`). `trace.reranked`, `trace.final` and `trace.dropped_below_floor` are filled in (`rag/retrieval.py:992-1003`), and `search` returns `(kept, trace)`.
14. **Generate.** `RagEngine.ask` calls `generate_answer` (`rag/engine.py:236`) — empty chunk list short-circuits to `NO_ANSWER` (`rag/generation.py:267`) — which builds system + capped history + grounded prompt (`rag/generation.py:225`, `rag/generation.py:54`) and calls Groq at temperature 0 (`rag/generation.py:270-275`). Streaming uses `stream_answer` (`rag/generation.py:285`), with `RagEngine.stream` emitting `sources` then `trace` then `token` events (`rag/engine.py:274-287`).
15. **Verify / diagnose.** `verify_citations` (`rag/generation.py:164`) turns every `[chunk_id=…]` in the answer into a set-membership test against what was actually retrieved. With `diagnose=True`, `classify_with_judge` (`rag/diagnostics.py:494`) rules separately on context sufficiency and answer groundedness (`rag/engine.py:251-256`); in the evaluator, `classify_with_ground_truth` (`rag/diagnostics.py:365`) does it deterministically from page-level labels.
